# 429 runbook

A 429 is never generated by Astro. It comes from Cloudflare, from Hostinger, or from our own PHP
endpoints (`download.php`, `mcp.php`). This page is how we tell those three apart and fix the right one.

## How a request travels

```
browser → Cloudflare (Server: cloudflare, cf-ray, cf-cache-status)
        → Hostinger CDN (platform: hostinger, x-hcdn-cache-status)
        → Apache/LiteSpeed + PHP on the shared plan
```

HTML is not edge-cached (`cf-cache-status: DYNAMIC`, `x-hcdn-cache-status: DYNAMIC`), so **every page
view reaches Hostinger**. The ISO installers are ~827 MB and ~977 MB and are bypassed by Cloudflare, so
**every Vision S download pulls about a gigabyte from the origin**.

## What this repo already does to reduce load

- `_astro/*` hashed assets: `Cache-Control: public, max-age=31536000, immutable`.
- Images, fonts, `.webp`, `.pdf`, `.zip`, `.apk`, `.exe`: 1 day to 1 year via `mod_expires`.
- `blog/posts.json` no longer uses `cache: "no-store"`, and JSON/XML get a 1-hour TTL.
- Markdown mirrors (`/index.md`, `.../index.md`) give crawlers a tenth of the bytes of the HTML.
- Our PHP endpoints rate-limit per IP and return `429` + `Retry-After` — if you see `Retry-After`, the
  429 is ours, not the CDN's.
- `/429.html` is the friendly origin-level error page (`ErrorDocument 429`).

## Step 1 — capture the evidence

In the failing browser: DevTools → Network → click the red request → copy as cURL, or read the
**Response Headers**. A Cloudflare block page also prints a **Ray ID** at the bottom; the header
`cf-ray` is the same value.

Then run the probe from the network that saw the error:

```bash
cd dicot-site
npm run probe:429 -- --url https://dicot.tech/ --count 30 --concurrency 5
npm run probe:429 -- --url https://dicot.tech/VisionS.iso --count 4 --concurrency 2
npm run probe:429 -- --url https://dicot.tech/ --accept text/markdown --count 5
```

The probe prints status, `cf-ray`, `cf-cache-status`, `x-hcdn-cache-status`, `retry-after` and a
verdict. If it cannot reproduce the 429, the trigger is burst-, IP-, geo- or bot-specific — rerun from
the same office/VPN connection and at the same time of day.

## Step 2 — read the headers

| Header / body | Meaning |
| --- | --- |
| `cf-mitigated: challenge` or a "Sorry, you have been blocked" body | Cloudflare challenge/WAF |
| `Server: cloudflare` plus a plain 429 body | Cloudflare rate-limiting rule, passed through |
| `platform: hostinger`, `x-hcdn-cache-status: ...` | Hostinger CDN/edge |
| Short/plain 429 body with `Server: LiteSpeed` | Hostinger origin (entry processes, CPU, bandwidth) |
| `Retry-After` present on `/download.php` or `/mcp.php` | our own limiter (expected under abuse) |
| 429 only on `googletagmanager.com` / `tawk.to` in DevTools | third party, not our origin — no site change |

## Step 3 — match the symptom to the fix

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| 429 on HTML only, body is a Cloudflare page | Rate-limiting rule / WAF / Bot Fight Mode | Exempt `/_astro/*`, images, fonts, `.md`, `.json`, `sitemap*.xml`; raise the HTML threshold; Security Level to Medium; turn Bot Fight Mode off (it fights the AI crawlers `robots.txt` invites) |
| 429 on HTML only, body is plain, `x-hcdn-*` present | Hostinger WAF / bot protection | hPanel → security logs; open a ticket with the timestamp + Ray ID + probe output |
| 429s cluster in the minutes after Vision S downloads | ~1 GB per download on a shared plan | move the ISOs to Cloudflare R2 on `dl.dicot.tech` and serve signed links (see README) |
| 429 only after N loads from one public IP (office NAT) | per-IP rate limit | raise the rule, or exclude static assets and `HEAD` |
| 429 from Cloudflare with `Retry-After` and a JSON body | our limiter | expected; tune `dicot_rate_limit()` limits if too tight |
| Googlebot/AI crawler 429s | crawl rate vs. origin | rely on the Markdown mirrors (cheaper), keep `Sitemap` accurate, do not increase origin caching of HTML unless you also solve markdown negotiation |

## Step 4 — do not create a new problem

Do **not** enable "Cache Everything" for HTML while `Accept: text/markdown` negotiation is active.
Cloudflare ignores `Vary: Accept` for HTML, so a cached HTML response would be served to agents that
asked for Markdown. If you need edge-cached HTML, move agents to the explicit `.md` URLs first and
purge on every deploy.

## Escalation

1. Cloudflare dashboard → Security → Events, filter by the Ray ID and by status 429.
2. Hostinger hPanel → Advanced → Logs / Resource usage at the same minute; include the probe output.
3. Record the outcome here so the next person does not start from zero.
